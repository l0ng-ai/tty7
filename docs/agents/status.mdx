An agent working for two minutes and an agent that stopped ninety seconds ago
waiting for permission look identical from outside. tty7 fixes that by letting
the agent say which one it is.

## Installing the hooks

**Settings → Integrations** lists every agent that can report status, with an
**Install** button beside each:

| Agent | |
|---|---|
| Claude Code · Codex · TraeCode · Copilot CLI · OpenCode · Pi · Grok Build · Oh My Pi · Gemini · Droid · Qwen Code · Goose · Kimi Code · Qoder CLI · Qoder CN CLI · Crush · CodeBuddy · Cursor CLI · Prime Agent · Antigravity · Empryo · Muse Code · jcode | Hooks available |
| Aider · Amp · Auggie · Hermes · Vibe | Detected and labelled, but no status channel yet |

Installing writes into that agent's own configuration directory. Once installed
the row grows a second **Uninstall** button beside the first, which itself
becomes **Reinstall** — or **Update**, against an **Outdated** state, when tty7
ships a newer hook.

<Note>
  Crush ships only a `PreToolUse` hook today. It is enough to remember the
  session for resume, but there is no turn boundary behind it, so a Crush pane
  carries no status dot and `tty7 wait` times out rather than returning.
</Note>

<Note>
  Antigravity has no session-start or permission event, so its pane goes
  straight from no dot to working on the first model call, and a pending
  permission prompt shows as working rather than amber. Its hooks live in a
  `tty7` set inside `~/.gemini/config/hooks.json`, beside any sets of your own.
</Note>

<Note>
  `cursor-agent -p` (print mode) sends neither of Cursor's turn hooks, so a
  headless run records its session id — Copy Session ID and resume still
  work — but shows no status dot. The interactive `cursor-agent` shows the
  full working → done cycle.
</Note>

<Note>
  The hooks only do anything inside tty7. Running the same agent in another
  terminal is unaffected.
</Note>

Hooks are installed per machine. Once a second
[machine](/remote/workspaces) is linked, a row of chips appears above the table
to pick which one you are looking at, and the table then shows that machine's
agents — so a dev box gets its hooks installed the same way, from the same
screen.

## Approval policy

A repo can list the shell commands its agents may run without asking, so you
stop approving the same `cargo test` in every session. Put a `.tty7/policy` at
the checkout's root:

```toml
[allow]
bash = ["cargo test*", "cargo check*", "pnpm lint", "git status", "git diff*"]

[ask]
bash = ["rm *", "git push*", "*sudo*"]
```

When Claude Code or Codex is about to ask for permission to run a `Bash`
command, tty7's `PermissionRequest` hook checks it against the policy. If an
`allow` rule matches and no `ask` rule does, the hook answers "allow" and no
prompt opens. Anything else goes to the agent's own prompt, exactly as it would
without a policy. The policy never denies anything, and it covers no tool other
than `Bash`. Your agent's own deny and ask rules still apply after it allows.

Each auto-allow shows as the pane's status message, for example *Allowed by
.tty7/policy (cargo test\*): cargo test -p core*.

### How commands are matched

The command is trimmed and compared as a whole.

| Pattern | Matches |
|---|---|
| `pnpm lint` (no `*`) | Only `pnpm lint`, exactly. |
| `cargo test*` | `cargo test`, and `cargo test` followed by a space and anything else. Not `cargo testify`. |
| `rm *` in `[ask]` | Anything the glob matches: `*` is any run of characters, anywhere in an `ask` pattern. |

- In `[allow]`, `*` may only come at the end of a pattern. Any spaces before it
  are ignored, so `cargo test *` means the same as `cargo test*`.
- A pattern ending in `*` never matches a command that contains `;` `&` `|`
  `` ` `` `$` `>` `<` `\`, or anything outside printable ASCII (a newline, a
  tab, a Unicode direction override). Those characters chain, substitute or
  redirect, so `cargo test; curl … | sh` is never covered by `cargo test*`. To
  allow a command that needs them, write the whole command as a literal
  pattern.
- `ask` rules always win. They are checked against the whole command and
  against each piece of it between shell operators, so a literal
  `make && rm -rf build` still prompts under `rm *`.
- No command that starts with `tty7`, and none that names the approvals file,
  is ever auto-allowed.
- `tty7 policy check '<command>'` prints the verdict and the rule that decided
  it. `tty7 policy show` prints the rules and whether they are in force.

<Warning>
  A prefix rule allows every argument the program accepts. `git diff*` covers
  `git diff --output=<file>`. `cargo test*` builds and runs whatever code the
  checkout contains. Only write prefix rules for programs you are happy to let
  an agent run with any arguments.
</Warning>

### Approving a policy

`.tty7/policy` is a file in the repo. Anyone who can get a commit in front of
you can write it: a project you cloned, a pull request from a fork, the agent
itself. So **a policy does nothing until you approve it**:

- Run **Agent: Review Repo Approval Policy…** from Search Everywhere on a local
  tab. It shows the rules and asks you to approve them. Or run
  `tty7 policy approve` in a terminal yourself. It shows the file and waits for
  you to type `approve`.
- The approval records the file's SHA-256 under the checkout's root path, in
  `policy-approvals.json` in tty7's config directory, not in the repo. Change
  one byte of the file and the policy is out of force until you approve the
  new content. Each checkout and worktree is approved separately.
- `tty7 policy approve` refuses to run without a terminal on stdin and stdout,
  and inside Claude Code's or Codex's shell tool. An agent's tool call cannot
  answer it.
- A file that does not parse, or that uses a table, tool or pattern tty7 does
  not recognise, is out of force as a whole. Nothing in it applies. Only
  printable ASCII is allowed, so what you approve is exactly what you see.
- `tty7 policy revoke`, or **Revoke** in the same dialog, withdraws the
  approval.

These steps keep the repo from approving its own policy. They cannot protect
you from an agent you have already let run arbitrary shell commands: such an
agent can edit tty7's config directory like any other file it can reach.

The check runs in the hook on the machine where the agent runs, and reads that
machine's approvals. Desktop review only covers local tabs. A policy in a repo
on a remote machine stays out of force unless you run `tty7 policy approve` on
that machine, which needs the tty7 CLI installed there.

## The status dot

Every tab chip and sidebar row carries a dot:

| Dot | Meaning |
|---|---|
| 🔵 **Blue** | Working |
| 🟠 **Amber** | Needs your input — a permission prompt, a question |
| 🟢 **Green** | Done with this turn |

<Frame caption="Working (blue), waiting on you (amber), and done (green), side by side">
  <img src="/images/agent-status.webp" alt="Agent status dots" />
</Frame>

The same three states are what `tty7 agents` reports as `working` / `waiting` /
`done`, and what [`tty7 wait`](/agents/orchestration) blocks on. A fourth state,
`idle`, carries no dot — it is an agent that has not started a turn.

## Notifications

Two, both following your **Settings → General → Notifications** policy:

- **"needs your permission…"** the moment an agent blocks on you
- **"finished after 42s"** at the end of a turn

Which means that by default — *When unfocused* — you are told the instant you
are the bottleneck, and left alone while you are watching.

A program can also post its own notification with OSC 9, OSC 777
(`notify;title;body`) or kitty's OSC 99. tty7 shows it under the same policy,
held back only while you are looking at that pane, and a click reveals the
pane. Claude Code writes one when its **Notifications** setting (`/config`) is
`ghostty`, `kitty` or `iterm2`. Its default, `auto`, sends nothing in tty7. A
pane whose agent already reports through tty7's hooks skips the copy that would
repeat the notice above.

## The tray icon

tty7 keeps a status item in the system tray (menu bar on macOS). It flips to an
attention state the moment *any* agent anywhere needs input, so you can see it
without the window in front of you.

Its menu lists every agent pane with its brand avatar and status dot — click one
to reveal it — and also holds the notification policy switch and **Quit and Stop
Server…**. An agent that needs input says for how long (*needs input · waiting
3m*), and the workspace switcher shows the same age beside its tab.

## Jumping to the agent that needs you

**Agent: Go to Next Needing Attention** (<kbd>⌘ ⇧ U</kbd>, <kbd>Ctrl ⇧ U</kbd>
on Windows and Linux; `FocusNextAgentNeedingAttention` to rebind) reveals the
agent pane that has been waiting on you longest, switching tab or window to get
there. It looks at the tabs open in your windows, the same agents the tray menu
lists; a workspace no window is showing is left out. Press it again for the next
one: every waiting agent, oldest first, then each finished turn you have not
looked at yet, and round again. With nothing waiting it says so and stays where
you are. Each wait is timed by the clock of the machine the agent runs on, so
agents on machines whose clocks disagree can show ages, and queue, slightly off.

Turn it off with **Settings → General → Show tray icon**
(`show_tray_icon: false`).

## Sending an agent some context

Two Search Everywhere actions hand what is in front of you to the agent running in
the pane, as a ready-made prompt:

| Command | Sends |
|---|---|
| **Agent: Send Selection** | The current terminal selection |
| **Agent: Send Git Diff for Review** | The repository's `git diff` |

If nothing recognisable is running, tty7 says *"No running coding agent found"*
rather than typing into your shell.
