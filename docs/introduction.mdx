tty59 is a terminal you can leave running. Close the window, reboot the machine,
walk to a different laptop — the shells you started are still there, and so are
the coding agents you left working in them.

It is written in Rust, renders on the GPU through Zed's
[gpui](https://github.com/zed-industries/zed), and parses VT with
[libghostty-vt](https://github.com/ghostty-org/ghostty) — Ghostty's
renderer-free terminal core. In practice that means full-screen output parses
several times faster than the engines it replaced, and a frame rate that does
not fall over when something floods the screen.

## How fast, exactly

Since the engine switch to libghostty-vt, the honest numbers are from the
machine that measured the switch — a Linux desktop (Arch, Wayland), same
session, five-run averages at the default 80×24 grid, the two engines side
by side through the whole GUI+pty stack:

| | **tty59 (libghostty-vt)** | tty59 (previous engine) |
|---|---:|---:|
| Plaintext I/O — 11 MB `cat` <sub>(lower is better)</sub> | **119 ms** | 127 ms |
| [DOOM-fire](https://github.com/const-void/DOOM-fire-zig) frame rate <sub>(higher is better)</sub> | 2372 fps | **2841 fps** |

At this small grid the fire test favors the cheaper-per-frame engine; at
200×50 the engine-level benches say full-screen parse is ~8× faster on
libghostty-vt. The against-Alacritty/Ghostty/Kitty table returns with the
first release of this engine, measured on the benchmark baseline machine.

The methodology and a one-command reproduction live in
[`scripts/bench/`](https://github.com/nathabonfim59/tty59/tree/main/scripts/bench).

Three decisions account for most of it:

- **The PTY is read at device speed** and parsed in large batches, off the
  render path — so drawing never throttles reading.
- **The hot paths are lock-free.** A big `cat` never waits on the renderer.
- **The server buffers up to 16 MiB** ahead of the window before backpressure
  applies, which is enough that a flood finishes writing while the window is
  still catching up.
